大模型训练、微调与推理框架全解析：从底层逻辑到工程落地

前言

在学习大模型相关技术的过程中，多数人都是从零散知识点切入：Transformer 原理、模型权重格式、各类训练与推理框架、端侧部署优化等。知识点看似都有所接触，但往往缺少一条完整的工程主线串联，导致概念混淆、边界模糊、无法形成体系认知。

本文基于个人长期碎片化学习积累与工程疑问，系统性梳理大模型训练（training）、微调（fine-tuning）、编译优化、推理（inference）全链路逻辑，统一厘清各框架、文件格式、部署场景的定位与差异，区分「训练侧建模逻辑」与「推理侧工程优化手段」。

旨在把零散的技术点沉淀为结构化知识体系，用于后续查阅、复盘与进阶深挖，为后续算子原理、推理优化、底层部署等细节学习建立顶层认知基础。

一、训练与推理的底层逻辑

大模型工程核心准则：先训练 / 微调，后推理；训练只做一次，推理无限复用。

训练（training）与微调（fine‑tuning）属于建模阶段：依靠海量数据集反复迭代更新模型内部权重参数，让模型习得知识、逻辑与业务能力。算力消耗大、耗时久，最终产出模型权重文件，训练完成后无需重复执行。

推理（inference）属于模型使用阶段：加载参数已经固定的模型权重到硬件，接收输入完成计算输出。推理过程不会修改模型任何参数，模型不会产生新的学习行为，是线上持续对外提供服务的核心环节。

完整基础链路：数据集 → 训练 (training)/ 微调 (fine‑tuning) 迭代优化权重 → 保存模型文件 → 推理 (inference) 引擎加载模型 → 对外提供 AI 服务。

补充概念说明： 还有一个词 prediction（预测），在传统机器学习经常使用；大模型领域工业实践，统一习惯叫 inference（推理）。

二、训练与微调生态

训练生态分为两层：底层基础计算框架负责张量运算；上层封装微调工具降低开发门槛，不用手写大量训练代码。

2.1 底层训练框架

表格

框架名称 特点 适用场景
PyTorch 开源社区主流，生态完善，资料丰富 互联网项目、绝大多数开源大模型训练 (training)
MindSpore 昇思 华为自研，深度适配昇腾 NPU 国产化项目、政企智算中心、盘古大模型训练 (training)

2.2 微调核心组件

表格

组件名称 定位 核心作用
PEFT HuggingFace 底层算法库 冻结基座模型，仅训练少量适配器参数；降低显存消耗，主流实现 LoRA、QLoRA 微调 (fine‑tuning) 算法
LLaMA‑Factory 上层一站式微调工具 封装 PyTorch+PEFT，提供命令行 / WebUI；开箱即用，输出 LoRA 适配器权重文件，需要搭配基座模型使用

训练生态层级：底层计算框架 → Transformers 模型基础库 → PEFT 高效微调核心库 → LLaMA‑Factory 上层应用工具

三、模型编译优化：训练 / 微调完成之后，推理之前发生了什么

核心疑问解答：原始训练出来的模型参数量巨大，原始权重体积大，端侧、边缘设备内存 / 显存不够，跑不动原始权重，于是就需要做推理侧编译优化。

✅明确结论：编译优化属于推理阶段前置的工程处理手段，发生在「微调结束之后，正式对外推理运行之前」。编译优化本身不做训练、不学习新知识，只改造模型的存储格式、计算逻辑，适配硬件、压缩体积、降低显存占用。

两种现实情况

  1. 不做编译优化，直接推理（云端 GPU 常用） HuggingFace、魔搭 ModelScope 社区原生safetensors权重，就是训练微调完直接导出的原始版本。 vLLM、TGI 可以直接加载原始权重直接跑推理 (inference)，不需要提前编译。 硬件显存足够的云上服务器，优先选择这种方式，部署简单灵活。
  2. 做编译 / 量化优化（端侧、边缘、低显存环境刚需） 原始大模型权重太大，边缘盒子、嵌入式设备、本地小显存显卡内存扛不住。 于是在正式启动推理服务之前，预先执行一套工程处理：量化、算子融合、计算图编译，输出适配硬件的专用模型文件。
  • 云端 GPU：原始 safetensors → TensorRT‑LLM 编译，产出 engine 文件
  • 国产化 NPU：原始 safetensors → 导出 ONNX → CANN 编译，产出 om 文件
  • 本地 CPU：原始 safetensors → GGUF 量化压缩

关于硅基流动、魔塔等平台标注的「优化后模型」： 平台上标注 “优化后” 的模型，就是别人已经提前把这套编译、量化工作做完，打包好上传的成品文件。 你下载下来可以直接给推理引擎加载，跳过你本地手动编译的步骤。

⚠重点：这个 “优化” 没有重新训练 (training)/ 微调 (fine‑tuning)，模型学到的知识、回答能力和原始模型完全一致；改变的只是：模型体积、显存占用、运行速度，部分量化版本会轻微损失一点点精度。

通俗类比：

训练微调：出厂原版高清电影（原始 safetensors 权重，体积巨大）

直接推理：高性能服务器直接播放原版高清片源

编译优化：把高清电影预先转码压缩成适配手机的版本（不改变电影剧情内容，只是体积变小，适配弱设备）

“优化后模型”：别人已经帮你转码压缩完毕，你拿到手直接播放，不用自己转码。

⚠关键认知：

  1. 编译、量化、转 ONNX，全部属于推理侧工程预处理，不属于训练环节，不会更新模型权重里的知识。
  2. 云端 GPU：编译优化是可选；端侧 / 边缘设备：编译优化基本是必选，硬件内存不足以承载原始权重。
  3. 编译优化后的硬件专属格式（om、engine、gguf），无法再拿回做训练 / 微调。

四、推理引擎生态

推理引擎：加载模型权重，优化速度、显存、并发，对外提供推理 (inference) 服务。分为云端服务器推理、端侧边缘推理两大场景。

云端服务器（Server / 云侧）：指机房高性能 GPU 服务器集群，算力、显存、内存充足。主要承载大模型高并发线上服务，追求吞吐、延迟、稳定性。云端场景一般不需要模型编译优化，可直接加载原始 safetensors 权重运行。

边缘侧（Edge）：介于云端和终端之间的中间设备，如边缘 NPU 盒子、工控机、本地机房小型算力设备。算力有限、带宽有限，需要对模型做编译、量化优化，降低资源开销，承担本地化推理、离线服务、国产化部署场景。

端侧（Terminal / 终端）：最终用户设备，手机、电脑、嵌入式板子、终端设备。内存极小、算力最弱、完全无法承载原始大模型，必须经过量化、编译、硬件适配才能运行推理。

总结：云端重服务、边缘重本地化、端侧重极致轻量化。

4.1 云端服务器推理

特点：面向线上大模型生产环境，追求高并发、低延迟；直接读取safetensors权重，编译优化为可选步骤，不是强制要求，不需要 ONNX 也可运行。

推理引擎 硬件依赖 核心特点 适用场景
vLLM NVIDIA GPU PagedAttention 分页注意力，显存利用率高，并发强，原生 OpenAI 兼容 API 开源大模型线上部署首选，可以直接加载原生权重，也可加载编译优化后的模型
TensorRT‑LLM NVIDIA GPU 深度压榨显卡硬件性能，性能上限高，需要做编译优化 高性能要求生产业务
TGI NVIDIA GPU 生态适配好，稳定性强，并发能力一般 HuggingFace 生态项目

4.2 端侧与边缘推理

特点：硬件种类多、算力偏弱，编译优化几乎是必做流程，依赖 ONNX 作为跨平台中间转换文件。 通用流程：训练权重 → 导出 ONNX → 编译为硬件专属模型 → 执行推理 (inference)

推理引擎 适配硬件 说明
ONNX Runtime CPU、通用 GPU、轻量 NPU 微软开源，通用 onnx 推理引擎
TensorRT NVIDIA GPU 多用于计算机视觉小模型推理，需要编译
OpenVINO 英特尔 CPU、英特尔 NPU 工控、边缘终端设备
CANN+MindSpore Lite 华为昇腾 NPU 国产化服务器、边缘 AI 盒子，输出 om 编译后模型
手机端推理库 手机芯片 高通 SNPE、苹果 CoreML 等，实现设备本地推理，必须编译适配手机硬件

五、模型文件格式

按用途分为：可训练格式、通用中转格式、硬件专属编译推理格式。

文件格式 核心用途 是否可继续训练 (training)/ 微调 (fine‑tuning) 适用场景
safetensors 存储完整模型权重 ✅ 支持训练 / 微调 训练、微调、云端推理，社区原始模型分发格式
LoRA 适配器 (safetensors) 存储增量微调权重 ✅ 支持迭代微调 LoRA 微调产出，依赖基座模型
onnx 跨框架模型中转交换 ❌ 仅推理 (inference)，不可训练 端侧、边缘设备部署，编译的中间产物
gguf 轻量化量化推理格式 ❌ 仅推理 (inference) 个人电脑本地离线推理，属于量化优化产物
om 昇腾 NPU 编译后离线模型 ❌ 仅推理 (inference) 华为昇腾硬件部署，编译优化输出
engine TensorRT 编译模型 ❌ 仅推理 (inference) NVIDIA GPU 硬件部署，编译优化输出

六、工程完整链路

  1. 互联网云端主流链路（两种分支）
  • 分支 A（快速上线，不做编译） PyTorch + PEFT + LLaMA‑Factory 完成微调 (fine‑tuning) → 产出 safetensors 权重 → vLLM 直接加载模型 → 启动 API 对外推理 (inference) 服务

全程不使用 ONNX，适配高并发大模型业务

  • 分支 B（生产高性能，增加编译优化） PyTorch + PEFT + LLaMA‑Factory 完成微调 (fine‑tuning) → 产出 safetensors 权重 → TensorRT‑LLM 编译优化 → 加载编译产物对外推理 (inference) 服务
  1. 国产化端侧部署链路（必须编译优化） 训练 (training)/ 微调 (fine‑tuning) 产出权重文件 → 导出 ONNX 通用格式 → 编译生成硬件专属模型文件 → 在边缘设备、NPU 硬件上执行推理 (inference)

补充平台 “优化后模型” 链路： 原始模型经过第三方预先完成编译 / 量化优化 → 上传至模型平台（硅基流动、魔塔等） → 用户直接下载优化产物，跳过本地编译，直接交给推理引擎运行。

七、常见认知误区

  1. ONNX 仅作为推理中转文件，不能够反向做训练 (training)、微调 (fine‑tuning)。
  2. PEFT 是底层算法库，LLaMA‑Factory 是上层封装工具，二者不属于同一层级。
  3. 推理 (inference) 阶段模型权重全程冻结，不会发生模型学习。
  4. 大模型云端部署优先选用 vLLM，ONNX 生态更多服务于端侧边缘设备。
  5. 编译优化 ≠ 重新训练：社区、模型平台标注 “优化后” 的模型，只是完成量化、算子编译预处理；模型本身知识能力不变，不会新增训练。编译属于推理侧的工程预处理手段，发生在正式推理运行之前。
  6. 编译优化不是所有场景都要做：显存充足的 GPU 服务器，可以直接跑原始 safetensors；内存紧张的端侧边缘设备，编译优化几乎必不可少。

结语

大模型工程的核心逻辑就是训练定型、推理复用。底层框架完成模型训练 (training)/ 微调 (fine‑tuning) 建模，vLLM 承担主流云端推理 (inference) 部署；编译、量化是推理侧前置工程预处理手段，用来适配硬件、降低内存开销，不改变模型本身能力；很多平台的 “优化后模型” 就是别人提前做完这套预处理的成品。各类端侧引擎适配多样化硬件，不同模型文件格式各司其职。理清整套链路，可规避多数概念混淆，为后续微调、部署落地打下基础。
