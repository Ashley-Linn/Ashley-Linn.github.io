从零到一搭建电影 RAG 系统：我的工程血泪史与工业实践复盘

花了一个月，踩了好多大坑。
一开始我沉迷完美规划：监控、缓存、单元测试、架构日志……结果代码完全看不懂。
后来发现模型不对，换模型后信心来了，却又被分块逻辑打回原形，越改越乱。
返璞归真重构项目，从数据清洗到双表对齐，翻译环节又坑了我：10块钱只跑了部分、Ctrl+C毁掉pickle文件、没有断点续传……
总算跑通MVP，最后引入RAGAS评估，指标低到怀疑人生，才发现检索器里藏着召回过滤——评估本应第一天就做。>
本文完整记录一个普通开发者如何从这些“软硬坑”中一步步走出来，最终建成了一个可量化、可落地的电影问答RAG系统。

一、为什么要做这个项目？

我一直对「检索增强生成」很感兴趣，但没有一个自己动手的全流程经历。电影剧情数据集（维基百科电影剧情，约 3.5 万部）结构简单、语义丰富，非常适合作为 RAG 的试验场。

目标很朴素：

  • 用户输入自然语言（如“时间旅行科幻电影”），系统能返回相关电影列表；
  • 并能基于检索到的剧情，用大模型回答具体问题；
  • 最终能用指标量化评估系统好坏。

听起来不难，但做起来才发现：工程实践中的坑，比算法本身多得多。

二、第一阶段：完美主义型规划，结果完全看不懂代码

一开始拿到一个现成的电影搜索项目，心想：我要把它改造成真正的 RAG。
于是开始疯狂规划：监控、缓存、单元测试、集成测试、项目架构、日志配置、单例模式……
甚至觉得用 claude Code 一写就能跑通。

现实：代码完全看不懂，不知道从哪下手。

实际做的努力：

  • 一行行拆解项目结构，理解每个模块在干嘛
  • 补习 pytest、fixture、测试执行脚本
  • 学习缓存实现、单例模式等概念

阶段性成果：成功启动了前端界面，也能做检索尝试。
但完全无法评估检索结果好坏，大脑一片混乱。

唯一收获：在这个“硬啃”过程中积累了很多工程化知识概念，为后面铺了路。

三、第二阶段：换对模型，信心第一次起来

某天发现检索返回的相似度极低（只有 0.3 左右）。
我最初用的是大家常推荐的轻量模型 **all-MiniLM-L6-v2**。它虽然支持多语言，但本质上更偏向英文语义，对中、英混合查询的跨语言对齐能力较弱。
我的数据是英文剧情，但用户查询往往是中文（或中英混合），这就导致跨语言检索效果很差。

解决：换为专门针对跨语言任务的多语言嵌入模型 **paraphrase-multilingual-MiniLM-L12-v2**。
只换一个模型名 + 重建索引（约 1 小时），相似度立竿见影提升到 0.7 以上。
这是我整个项目中最具性价比的一次优化。

换模型后发现的遗留问题（“语言混杂陷阱”）：

  • 纯英文或纯中文查询：相似度都很高，两者表现类似。
  • 中英混合查询（如“time travel 电影”）：在小规模脚本测试中，相似度有时甚至更高；但在大规模真实数据统计时，却出现了明显下降。

根本原因：多语言模型对混合语言输入的鲁棒性有限，混合输入会被映射到“模糊区域”，既不完全靠近英文剧情也不完全靠近中文剧情，导致余弦相似度降低。小样本测试可能因偶然匹配或数据分布偏差掩盖了这一真实问题，大规模统计才能暴露本质。

考虑到系统主要面向中文用户，纯中文效果已可接受，且修复混合查询的成本较高，我决定暂不处理，只做记录。

教训：

  • 跨语言 RAG 中，嵌入模型的跨语言能力优先于分块、重排等任何其他优化。
  • 小样本测试可能掩盖真实问题，必须在大规模数据上验证。
  • 不是所有坑都要立即填——“足够好”有时比“完美”更明智。

四、第三阶段：分块逻辑，从暴力到语义边界

模型对了，但检索结果依然不理想——尤其长剧情电影，返回的块前言不搭后语。

问题现象

  • 固定 chunk_size=800，overlap=100，对所有剧情一视同仁。
  • 长剧情（>5000 字符）被切成几十个碎片，因果链断裂。
  • 短剧情（<200 字符）被过度切分或丢弃。
  • 经常出现单词被切断。

解决方案：语义边界自适应分块

我手写了一个 SmartTextSplitter，采用迭代队列方式，按分隔符优先级从大到小切分，并尽量拼接，保证不切断句子。核心逻辑：

策略 实现
短文档保护 完整文档且长度 < 200 字符 → 直接整块，不切
优先级分隔符 \n\n → \n → . ! ? → ; , → 空格，逐级切分
尽量拼接 在不超过 chunk_size 的前提下，尽可能多地合并同一级分隔符切出的片段
兜底暴力切分 若所有分隔符都不存在，才按固定长度切分（此时可能切断单词，极少发生）
碎片合并 合并长度 < 40 字符的碎片到前一块（不超过 chunk_size）
最后统一加重叠 所有分块完成后，只在最后一步添加一次重叠，且在空格处断开，避免切词

效果：块完整性大幅提升，检索返回的片段可读性明显增强，大部分剧情保持在 3~5 个语义完整的块内。

评估分块质量（事后才做）

跑 evaluate_chunks.py 发现：

  • 平均长度 620 字符（偏长，但仍在模型窗口内）
  • 完整句子结尾比例仅 76% —— 部分因原始数据本身缺少句号，不是分块算法的问题。
  • 少数单词切断现象（因回退到暴力切分，且仅在极特殊文本中触发）。

被忽略的基建：数据清洗后必须输出报告

在重构项目时，我做了数据清洗、去重、生成唯一 mvid。但在项目后期回顾时，我才意识到：我从来没有在清洗后生成一份数据质量报告（比如缺失值分布、剧情长度分布、异常样本展示）。
这是所有数据工程的基础——你必须足够了解自己的数据。如果清洗后仍有大量脏数据（比如剧情为空的电影、异常标点的句子），会直接污染后续分块、检索、摘要生成。
建议以后任何项目，数据清洗完成后都要输出一份简易报告（可用 pandas-profiling 或自己写统计脚本），并抽样人工检查。这一步被我忽略了，但却是最不该省的。

教训：分块质量评估不应该等全部开发完才做，一开始就要建基线。而数据清洗的质量评估同样应该在第一步就完成。

五、第四阶段：摘要生成，从 LSA 到位置加权 TextRank

原始剧情太长（平均 2000+ 字符），需要生成短摘要展示给用户。

最初方案：LSA（潜在语义分析）

最初尝试了 LSA 抽取式摘要。

  • 速度快，实现简单。
  • 但生成的摘要常常从中间开始，缺少故事开头；句子之间逻辑跳跃，甚至出现“乱七八糟”的拼凑感。
  • 超长文本需要分块多次 SVD，效率低，且质量并没有明显改善。

显然，LSA 不适合电影剧情这种强叙事、强时序的文本。

最终方案：位置加权 TextRank + 强制保留第一句

放弃 LSA，改用 位置加权 TextRank，并在代码中强制保留第一句话（无论算法得分如何）。核心参数：

参数 值 说明
top_n 5 抽取 5 个句子
pos_weight 0.3 30% 分数来自位置先验（指数衰减）
max_len 800 字符 确保摘要不频繁截断
强制第一句 是 无论 PageRank 分数，第一句必须入选

效果：摘要连贯性、信息完整性明显优于 LSA，且不再“从中间开始”，用户可读性大幅提升。

算法对比（精简版）

  • TextRank：图排序，句子作为节点，相似度为边，跑 PageRank。
  • LexRank：类似 TextRank，但使用 TF‑IDF 加权余弦相似度。
  • 位置加权 TextRank：额外给前面句子指数衰减先验，更适合强叙事文本。

教训：摘要生成必须结合实际数据特点（电影剧情强时序），不能只依赖通用库的默认参数。如果发现算法效果明显不合理，要果断更换方案，而不是硬调参数。

六、第五阶段：翻译，折腾又花钱

为了展示中文摘要，需要将英文摘要翻译成中文。最初想全量翻译 3.5 万部，但折腾了太多坑，最终只选了 2000 部进行效果验证。

血泪折腾史

  • 百度翻译：先免费额度，后又充了 10 块钱，额度用的很快，没跑完就失效。没有断点续传，白跑白费钱。
  • 有道翻译：为了免费额度，换了有道，结果 API 接入就卡住了：签名必须按官方隐藏规则（前 10 字符 + 文本长度 + 后 10 字符），否则一直报错。好不容易调通，又因为保存策略不对，频繁 Ctrl+C 中断直接毁掉 .pkl 存档文件（wb 模式打开文件瞬间清空，新内容没写入就中断 → 文件残缺）。
  • 离线翻译（MarianMT）：想省掉 API 费用，试了 Helsinki-NLP/opus-mt-en-zh。质量实在太差，译文不通顺，无法用于展示。
  • 腾讯云翻译：最后尝试腾讯云 API。接入过程也挺折腾：需要开通子账户、配置密钥。好在有 500 万字符免费额度，足够覆盖我的验证量。最终成功跑通，译文质量可接受，支持断点续传、原子保存，完成了 2000 部的翻译验证。

解决方案

  • 原子保存：先写临时文件，os.replace() 再重命名，防止中断毁档。
  • 断点续传：每翻译一条就保存一次，记录已翻译的 mvid，重启脚本不重复翻译。
  • 最终选择：腾讯云翻译（免费额度 + 质量稳定），放弃全量翻译，仅验证 2000 条。

翻译质量评估

我没有做自动指标（BLEU 太麻烦），而是采用人工抽样评估：随机抽取 50 条摘要，对比中英文语义一致性，确认腾讯云译文可接受。

经验：批量翻译任务，第一原则是原子保存 + 断点续传，否则钱和时间都白花。不要迷信离线模型，质量不达标一样没用。接入第三方 API 时，预留足够的时间折腾签名、子账户等坑。优先选择有免费额度的服务，可以大幅降低试错成本。

七、第六阶段：检索优化从类型微弱加权到双表对齐与混合排序

早期弯路：类型微弱加权与放弃

在优化检索时，我发现前端返回的电影类型与剧情经常对不上。于是我统计了高频类型（科幻、喜剧、悬疑等），想给匹配类型的电影加上微小权重（0.02）。
但实测发现，类型字段本身质量很差：即便统计了分布，加权后检索质量不升反降。
我一度不想放弃，又仔细评估了字段质量，发现确实不可靠。最终决定完全放弃类型加权，只在用户界面增加一条备注：“官方标签可能与剧情不完全匹配”，提醒用户自行判断。

这个插曲让我明白：不是所有字段都适合参与排序，低质量数据引入只会带来噪声。

第一步：标题硬置顶

既然类型不可靠，那用户搜电影名时该怎么办？
我加了一个硬规则：如果查询词与某部电影的标题完全匹配（忽略大小写），无论剧情相似度高低，直接将这部电影置顶。
这解决了“搜电影名找不到”的痛点，但对“剧情描述”没有帮助。

第二步：标题向量检索 + RRF 融合

仅仅硬置顶还不够。用户可能搜“悬疑电影”，如果某电影标题里恰好有“悬疑”，也应该被召回。
于是我为所有电影标题单独建了一个 FAISS 索引。检索时，同时得到剧情向量排序列表和标题向量排序列表，用 RRF（倒数排名融合） 合并两个列表。
RRF 不用归一化分数，只依赖排名，实现简单且效果稳定。
此外，标题完全匹配时的硬置顶逻辑依然保留，作为最高优先级。

效果：电影名查询命中率从“经常找不到”变成“永远第一”，剧情描述查询也能借助标题语义辅助，召回更加全面。

最终架构：双表对齐（索引-元数据分离）

在优化检索的过程中，我还重构了底层存储：

  • FAISS 索引只存向量，以及一个与向量顺序一致的 mvid_list。
  • 元数据（标题、年份、摘要、翻译等）独立存放在 movie_info 字典中，以 mvid 为主键。

优点：

  • 更新摘要或翻译无需重建向量索引。
  • 可并行维护多个版本元数据（LSA / TextRank / 中英文），检索时只需切换加载文件。
  • 索引文件小，部署方便。

八、第七阶段：评估体系，RAGAS 的坑与顿悟

项目快做完时，我才开始引入 RAGAS 框架做量化评估。

踩坑 1：测试集构建——LLM 生成完全不行

一开始我偷懒，用 LLM 自动生成 (question, ground_truth, contexts)。结果完全不行：生成的问题与答案模糊，无法反映真实检索效果。
顿悟：评估数据集必须手工构建，至少 10~20 条黄金样本。ground_truth 要从原文直接截取，长度与预期答案相近。

数据集构建原则（重要）

  • 答案必须清晰、无歧义：每个问题的标准答案必须能从原文直接定位，不能模糊。
  • 引入负样本：随机添加一些与问题不相关的电影剧情，测试检索器的拒答能力。
  • 核心基线必须手工标注：10~20 条黄金样本是基石，无论如何不能省。
  • 后续扩展可半自动：
    • 模板化生成（如从结构化字段抽取 导演、年份 等事实型 QA）。
    • 使用 RAGAS 自带的 TestsetGenerator 基于文档生成合成数据。
    • 引入外部 QA 数据集（如 DoQA）进行泛化验证。
  • 人工抽检不可替代：任何自动生成的数据集，最终都要人工抽查 20% 以上，确保质量。

踩坑 2：检索器返回的内容与索引不一致

索引里存的是完整分块（chunk_text），但检索器返回给生成器的顺序是：
Plot_summary_zh → Plot_summary → Plot_cleaned 前 350 字符。
这导致生成器接收到的信息严重丢失，端到端评估指标极低。

我单独测试了生成器（直接给完美上下文），其答案质量可达 90% 以上；而标题检索的召回率本身也不理想。
最终我接受了这个现状，没有进一步优化检索器返回策略，因为项目已近收尾，且核心功能已可用。

测出的真实数据（端到端）

指标 得分 含义
context_precision 0.28 检索到的 3 个片段中，真正相关的比例低
context_recall 0.30 标准答案的关键信息，只有 30% 被检索到
faithfulness NaN 生成答案多为“无相关信息”
answer_relevancy 0.20 答案与问题相关性差

顿悟：瓶颈完全在检索环节。生成器本身很强，但被不充分的上下文拖累。

RAGAS 使用教训

  • 版本锁定：RAGAS 框架更新频繁，接口经常变动。我最终锁定 **ragas==0.2.2**，避免升级带来的兼容问题。
  • **必须提供 ideal_contexts**：评估 context_recall 需要手工标注希望检索器返回的证据句。
  • 评估应该从项目第一天就开始：先裸跑基线，每加一个优化就测一次，而不是最后才补。

九、第八阶段：部署与工程化，异步加载模型的致命坑

问题现象

用 FastAPI + uvicorn 启动服务，模型加载时报错：

根源

  • SentenceTransformer 底层用 httpx 发请求检查远程更新，即使本地有缓存。
  • 在 run_in_executor 的线程池中初始化模型，httpx.Client 生命周期与事件循环冲突，导致连接关闭。

真正唯一有效、一劳永逸的解决方案：

十、关于提示词与前端交互的额外觉悟

提示词模式：严格 vs 自由

在测试智能问答时，我发现同样的问题，用“语义搜索”找不到答案，但用大模型“自由生成”却能答出来。
这说明大模型有很强的“创造发挥”能力——如果不加约束，它会在没有检索信息的情况下自己编造答案。
于是我把问答模式拆成两种：

  • 严格模式：只基于下方检索到的上下文回答，信息不足时直接说“无法回答”。
  • 自由模式：可以结合自己的知识发挥，适合开放性问题。

并且在前端侧边栏提供开关，让用户自己选择。
教训：提示词不是写一次就完事，要根据实际效果反复打磨，主动预设模式并让用户可见。

前端展示逻辑：不要让用户猜

在语义搜索结果列表中，每部电影会显示一个“相似度”分数。但用户可能会困惑：为什么有的相似度是 0.00？为什么官方标签和剧情对不上？
针对这些问题，我在侧边栏增加了固定备注：

  • 相似度分数仅表示剧情匹配程度，0.00 表示仅标题语义匹配、剧情不相关。
  • 官方标签（Primary_Genre）可能与实际剧情不符，仅供参考。
  • 智能问答分为“严格模式”和“自由模式”，解释各自行为。

这些微小的说明，大大降低了用户的学习成本，也避免了对系统能力的误解。
教训：任何可能让用户疑惑的数据或逻辑，都要在前端加注说明，这是产品思维的体现。

十一、最后的血泪总结

  1. 数据清洗后必须输出质量报告：足够了解自己的数据是一切工程的基础。
  2. 双表对齐（索引与元数据分离）：工业界通用实践，能极大降低迭代成本。
  3. 多语言检索：嵌入模型的跨语言能力比任何调参都重要。
  4. 翻译批量任务：原子保存 + 断点续传是底线，否则钱和时间都白费。
  5. 评估体系必须前置：先裸跑基线，每步优化都测量，避免“最后发现自己白做”。
  6. 异步部署：模型加载必须在主线程，且强制离线。
  7. 提示词要主动预设模式（严格/自由），并在前端给用户清晰说明。
  8. 前端备注是产品思维：不要让用户猜，不要让用户困惑。

十二、写在最后

回头看这一个月的开发周期，我并没有一开始就走最优路线，而是在完美主义、盲目堆架构、无效调参里绕了很远的路。

RAG 系统从来不是单一算法的比拼，而是数据质量、嵌入选型、文本分块、检索融合、工程容错、量化评估、产品交互的全链路工程综合体。

对个人开发者而言，最小可行的 MVP 永远优先于理想化的完美架构。

先跑通、再优化、后量化，才是低成本试错、持续迭代的正确节奏。

这个三万五千条电影剧情 RAG 项目，没有精致的包装，没有亮眼的 star，却是我从零到一完整走完 RAG 工业落地流程的真实沉淀。

所有踩过的坑、记下的教训、落地的方案，都会变成后续复杂 AI 应用开发的底层经验库。

技术学习从来不是一蹴而就，那些混乱、卡顿、反复重构、花钱踩雷的时刻，最终都会变成扎实的工程能力。

项目暂时告一段落，但迭代不会停止，后续会基于本次评估短板，持续优化检索召回、补充高质量标注数据集，慢慢打磨成更稳定、更完善的个人实践作品。
